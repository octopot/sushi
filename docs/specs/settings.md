# The settings window

**Status:** describes Sushi v0.3.0 as implemented. Rules marked with an ID hold today and are checked by the tests listed under [Verification](#verification); the parts that go through the window server are checked by hand, with the [regression scenarios](panel.md#regression-scenarios) of the panel.

Everything Sushi knows lives in plain files ([local files](local-files.md)), and they stay the source of truth. The settings window is an interface over the same files: it shows what each file holds and what is in effect, and writes a change back to the file the moment it is made. A file edited by hand keeps working and shows in the window the next time the window gets focus. This document fixes how the window opens and closes, how it reads and writes the files, what each pane offers, and how the window and the panel share the keyboard. The formats themselves stay in [local-files.md](local-files.md); the model, its providers and the connect flows in [model.md](model.md).

## Terms

- **The window** — the settings window, titled *Sushi settings*. **The panel** is Sushi's prompt panel ([panel.md](panel.md)).
- **Pane** — one of Keyboard, Model, Actions, Library and About. The Library pane also holds the Dictionary.
- **Section file** — the file a pane or a part of it shows: `hotkey.json` (Keyboard), `model.json` (Model), `rules.json` (Actions), `library-path.txt` and `dictionary.json` (Library), `diagnostics.json` (About).
- **Revision** — what a read saw of a file: a hash of its bytes, or *absent* for a missing file.
- **Draft** — what the user typed or chose in the window and Sushi has not written yet.
- **Sushi's writers** — every part of Sushi that writes a settings file: the window, the Model menu, the connect and disconnect flows, the move of the v0.2.1 key, starting a file over and the first-run seeding.
- **Key in effect** — the key that shows the panel right now ([LF-18, LF-19](local-files.md#hotkeyjson--the-key-that-shows-sushi)), which may differ from the one chosen.

## Rules

### Opening and closing

- **ST-1. One window.** **Settings…** in the menu bar menu and ⌘, in the panel, in any of its views, open the window. **About Sushi** opens it at About, **Model settings…** and **Fix model settings…** at Model, and the row that reports a problem with the key ([PN-7](panel.md#the-menu-bar-menu)) at Keyboard. There is one window: the first request makes it, a later one brings the same window forward and shows the pane asked for, with what the user left in the other panes. It is a normal resizable window, 760 × 560 points at first and at least 680 × 460, and it follows the system's light or dark appearance.
- **ST-2. It takes the keyboard.** Opening the window makes Sushi the active app, moves the window to the Space the user is in and gives it the keyboard. The panel hides first, without giving the keyboard back to the app underneath ([PN-9](panel.md#hiding)). Sushi still has no Dock icon.
- **ST-3. Closing.** ⌘W and the close button hide the window; it is not destroyed, so the next open finds the panes and their drafts (ST-9) as they were. The panel does not show. When Sushi had the keyboard, the app the user was in before the window or the panel took the keyboard becomes active again; a window closed while another app is active activates nothing.
- **ST-4. Panes and keys.** A sidebar lists the five panes; ⌘1 to ⌘5 show them in that order. Every control can be reached with the keyboard and has a name VoiceOver reads. Esc ends what the focused control is doing, such as recording a key (ST-16) or a confirmation, and never deletes or resets anything. ⌘Z outside a text field undoes the latest deletion (ST-24, ST-28); inside a text field it is the field's own undo.

### Reading

- **ST-5. Fresh reads.** The window reads every section file when it opens, every time it gets focus, and when another part of Sushi changes something it shows: the Model menu, a connect or disconnect flow, a `hotkey.json` applied at launch or after a reset, a recording of the key that Sushi ended by itself (ST-16), a problem report starting or ending its recording. Each read also asks the keychain which providers have a key, so a key deleted in Keychain Access shows, applies a `diagnostics.json` edited by hand, as a show of the panel does ([LF-21](local-files.md#diagnosticsjson--recording-why-the-panel-hid)), with the menu following, applies a `hotkey.json` edited by hand since Sushi last applied it, and, when the chosen key is not in effect for a reason outside Sushi or no key is active, tries the chosen key again ([LF-18](local-files.md#hotkeyjson--the-key-that-shows-sushi)). A read seeds a missing `rules.json` or `dictionary.json` as any first use does ([LF-3](local-files.md#settings-folder)) and creates nothing else: the library's folder is counted, not created.
- **ST-6. What a file can be.** Each section file is in one of five states, and the pane says which; the line under the section (ST-7) names the state: *Using defaults* or *Not created yet* for an absent file, *Needs fixing*, *Cannot be read*, *A link*:
  - *present and valid* — the pane shows its values and its controls write;
  - *absent* — the pane shows what Sushi uses without the file (Caps Lock with ⌃⇧Space, Ollama, the default library folder, logging off) and its controls write, creating the file;
  - *invalid* — the validator Sushi reads the file with rejects it: ST-13;
  - *unreadable* — permissions or a folder in its place: the pane says *Sushi cannot read <file>.*, keeps the system's message under **Error details**, and offers **Open settings file…** and **Show in Finder**; its controls do not write, and nothing offers to start the file over;
  - *a symbolic link* — ST-14.
- **ST-7. Every section names its file.** Under each section a quiet line names its file and its state, with **Show in Finder**, which selects the file, or opens the settings folder when the file does not exist, and **Open in editor**, which opens it in the default text editor when it is a regular file. While the file is not valid, readable and a regular file, the banner of ST-13 or ST-14 carries these ways to the file instead.

### Saving

- **ST-8. Saved when made.** There is no Save button. A change is committed when the user leaves the field or presses Return in a one-line field, clicks a control (a switch, a choice, a button), or, for a new action or term, once the record is complete and valid. Return in a multi-line field is a line break. A committed change is checked by the same validator Sushi reads the file with, then written; *Saved* shows briefly at the top of the pane. Saves of one file run one at a time, each with the revision the previous one left. A value the validator rejects is never written: the field says what is wrong next to it, and the file stays as it was. A save that fails says so beside the list or the field, as *Not saved: <the reason>*. The rules each file follows after the write are those of [LF-2, LF-18, LF-20, LF-21 and LF-11](local-files.md).
- **ST-9. Drafts.** What is typed and not valid yet stays in its field as a draft marked *Not saved*, with the reason beside it, and the pane's entry in the sidebar shows that it holds something not in its file. A read of the files (ST-5) refreshes every pane that has no draft: a change made outside Settings to a pane without a draft simply replaces what the pane shows. A read never throws a draft away, a phrase typed and not yet added included, and a read that started before a save never undoes that save on screen. A record the user empties while its save is on its way stays in the file as that save wrote it: the saved version becomes the row's original, the emptied row is a draft against it, and the next write of the list keeps it. Drafts live as long as Sushi runs: closing the window keeps them, quitting Sushi drops them.
- **ST-10. Never over a change it has not seen.** Every save carries the revision the pane was read at. Sushi's writers go through one path that holds a lock per file and, under it, reads the file, compares it with the revision and only then writes; when the file differs, nothing is written. The reply of every save describes exactly what that save wrote: its revision and its values come from the bytes written, never from a later read. So when anyone edits the file right after Sushi's write, the pane does not take that edit for its own, and the next save meets it as a conflict (ST-11). The Model menu and the connect flows have no revision to carry: they decide from what they read under the lock. No lock is held while a browser sign-in, an alert, a folder picker or a network request waits. The one limit: Sushi checks the revision, then replaces the file; a text editor that saves in the moment between the two loses its change.
- **ST-11. A file that changed under a draft.** When the file of a pane with a draft changes, whether a read notices it or a save is refused for it (ST-10), the pane keeps the draft beside the file's new contents and says *<Section> changed outside Settings.*, such as *Actions changed outside Settings.* A phrase typed and not yet added counts as a draft of its action: when that action changes or disappears in the file, it is a conflict too. The banner offers **Use the file's version**, which drops the draft, and **Replace with my version**, which saves the draft over the new revision, through the validator. For Actions it also says what differs: how many actions the file and the draft hold when that differs, and which actions the file changed or removed, by name. For the dictionary it compares the number of terms when they differ; other panes name no difference. A conflict found after a folder was chosen (ST-27) offers **Choose again…** instead of **Replace with my version**, since the choice was not saved. Nothing retries by itself. An undo of a deletion (ST-24, ST-28) goes through the same check.
- **ST-12. How a file is written.** A write replaces the whole file at once, through a temporary file in the settings folder, so a reader sees the old contents or the new ones, never a part. A file Sushi writes has permissions 0600. Sushi writes `rules.json` and `dictionary.json` with one entry per line, as the [examples](examples/) are, `hotkey.json`, `model.json` and `diagnostics.json` as indented JSON, and `library-path.txt` as one line; the layout of a file written by hand is not kept.
- **ST-13. An invalid file.** A pane whose file is invalid says which feature could not be loaded (*Actions couldn't be loaded.*), what Sushi does meanwhile, from the state it is really in, and how to recover; the validator's message, as the panel shows it, is under **Error details**. The other panes work as usual. What Sushi does meanwhile:

  | File | The banner says |
  | --- | --- |
  | `rules.json` | Sushi keeps using the actions it read before. |
  | `dictionary.json` | The Library keeps the terms it read before. |
  | `hotkey.json` | *Meanwhile <the key in effect> shows Sushi.*, or *No key shows Sushi meanwhile.* |
  | `model.json` | *Edits are stopped until it is fixed.*; no row of the Model pane is *In use* ([MD-3](model.md#choosing-the-provider)). A linked `model.json` that does not validate stops edits the same way (ST-14). |
  | `library-path.txt` | *The Library cannot open until the path is fixed.* |
  | `diagnostics.json` | What Sushi does now: *A problem report is recording, so the log is still written.*, *The log is still being written.* while the mode stays on as it was ([LF-21](local-files.md#diagnosticsjson--recording-why-the-panel-hid)), or *Nothing is logged meanwhile.* |

  It offers **Open settings file…**, **Show in Finder** and a reset named for the file: **Restore default actions…**, **Restore default dictionary…**, **Restore default shortcut…**, **Restore default model…**, **Use the default folder…** or **Turn logging off…**. The reset asks first and says that a copy of the current file is kept. It then keeps the broken bytes next to the file as `<stem>.invalid-<UTC time>.<ext>`, such as `rules.invalid-20261124T101500Z.json` (0600; `-2`, `-3` … are added when the name exists), puts the shipped [example](examples/) in place of `rules.json`, `dictionary.json` or `hotkey.json`, and removes `model.json`, `library-path.txt` or `diagnostics.json`, so Ollama, the default library folder and no logging are in effect. It is refused for a valid file and for a file that changed since the pane read it, and is not offered for an unreadable file or a link. A restored `hotkey.json` registers its key at once, and the menu follows a restored `model.json` or `diagnostics.json`.
- **ST-14. A linked file.** A section file that is a symbolic link is read and shown, and never written, by the window or by any other of Sushi's writers: the pane says *These settings are managed in another file.*, its controls do not write, and it offers **Edit original file…** and **Show link in Finder**. When the file it points to is not valid, the pane adds that Sushi cannot use it as it is, with the validator's message under **Error details**.

### Keyboard

- **ST-15. The choice.** *Show Sushi with* chooses **Caps Lock** or **Keyboard shortcut**, and saves at once (ST-18). With Caps Lock chosen, the combination stays shown as the *Backup shortcut*: Sushi registers it when it cannot take Caps Lock ([LF-19](local-files.md#hotkeyjson--the-key-that-shows-sushi)).
- **ST-16. Recording a combination.** **Change…** starts recording, only while the window is in front with the keyboard; otherwise Sushi refuses: *Sushi records a combination only while the Settings window is in front.* Recording starts once Sushi has paused the key in effect: while it records, that key does not show or hide the panel; Caps Lock stays mapped and the key it arrives as is ignored, and a combination in effect records instead of toggling. The user presses the combination; it is taken when all its keys are released, and a second key pressed while it is held does not replace it. Esc cancels; Tab and ⇧Tab leave the recorder, as they leave any control; a click elsewhere ends it. A key without ⌃, ⌥, ⇧ or ⌘ is refused (*Hold Control, Option, Shift or Command with another key.*), a modifier alone or Fn alone is not a combination, F18, the key Caps Lock arrives as, is never part of one, and a key held down does not repeat. The key is read by its position, so the same combination is recorded with any keyboard layout. Recording also ends when the window loses the keyboard, hides or reloads its page, and by itself after 60 seconds; when Sushi ends it, the pane says *Recording stopped. Click the shortcut to record again.* When recording ends, Sushi registers the key in effect again only once that key's own keys are up, however long they are held, so a combination still held from recording never toggles the panel. While recording runs or Sushi waits for those keys, a read of the files (ST-5) registers nothing; once the keys are up, the key is registered and `hotkey.json` is applied as it is then. **Restore ⌃⇧Space** next to the recorder puts back the default combination.
- **ST-17. What is in effect.** A status line says which key shows Sushi now, from the same state as the menu ([PN-7](panel.md#the-menu-bar-menu)): *<key> shows Sushi.* When that is not the key chosen, or no key is active, it leads with the cause, then the key that works (*Use ⌃⇧Space to show Sushi.*), then what to do:

  | Cause | The line leads with | What to do |
  | --- | --- | --- |
  | macOS switches input sources with Caps Lock | *Caps Lock is used to switch input sources.* | *To use Caps Lock, turn off “Use the Caps Lock key to switch…” in System Settings ▸ Keyboard ▸ Input Sources.*, with **Open macOS keyboard settings…** |
  | Another app maps Caps Lock | *Another app already remaps Caps Lock, so ⌃⇧Space shows Sushi.* | *Quit the app that remaps Caps Lock, or choose a combination.* |
  | Caps Lock's key could not be registered | *Caps Lock could not be registered, so ⌃⇧Space shows Sushi.* | *Choose a combination, or quit Sushi and open it again.* |
  | The combination could not be registered | *No key shows Sushi: ⌃⇧Space could not be registered.* | *Choose another combination: another app may already use this one.* |
  | `hotkey.json` is invalid | the file's banner (ST-13) | Fix the file or restore the default; until then the key in effect stays. |

  The combination named is the one of the file. In the first three cases Sushi tries Caps Lock again each time the window reads the files (ST-5): once the cause is gone, coming back to Settings is enough. With Caps Lock in effect, the combination is labelled *Backup shortcut* and *Used if Caps Lock is unavailable.*; while Sushi uses it instead, *In use now, because Caps Lock is unavailable.*
- **ST-18. Saving the key.** A change of the key is one step: the combination is put in its canonical spelling ([LF-18](local-files.md#hotkeyjson--the-key-that-shows-sushi)), the new key is registered, and only then is `hotkey.json` written. With Caps Lock in effect, a changed backup combination is registered once and released again before the write, so it is checked too. A backup Sushi registered and could not release again is not saved either: *Sushi tried ⌥Space and could not release it again: it was not saved. Caps Lock still shows Sushi. ⌥Space may also show Sushi until Sushi quits.*, or *Sushi tried ⌥Space and had trouble releasing it: it was not saved. …* when it was released in the end. A combination Sushi cannot register is not saved, whether it is the key in effect or the backup: the previous key is registered again, and the message says what works now (*Sushi could not register ⌥Space: it was not saved. Caps Lock still shows Sushi.*, *… ⌃⇧Space still shows Sushi.*, or *… No shortcut is active.*). When the file cannot be written, the previous key comes back the same way.
- **ST-19. The keys of the panel.** Under *Panel shortcuts*, which says *These shortcuts cannot be changed.*, the pane lists the keys of the panel in the groups and words of the [keyboard guide](../content/guide/keyboard.mdx): *In the panel*; *Versions*, with its condition *Right after an edit or a step, until you type.*; *Actions list (⌘K)*; and *Library (⌘L)*, including ↑ ↓ and ↵.

### Model

- **ST-20. Where edits run.** The pane lists Ollama, OpenRouter, OpenAI and Claude, one row each; ↑ and ↓ move between the rows. A row opens its details in place; looking at a row never changes the provider. The active provider carries *In use*, and one that is active without a key says *In use, but no key is saved*. With an invalid or unreadable `model.json`, or a linked one that does not validate, no row is in use, since edits are stopped (ST-13). *Connected* means a key is stored, in the keychain or, from v0.2.1, in `model.json` ([MD-12](model.md#connecting-a-provider)); it says nothing about whether the key or the account still works.
- **ST-21. Choosing.** **Use for edits** on Ollama or on a connected provider writes `provider` to `model.json` ([LF-20](local-files.md#modeljson--the-model)); the Model menu follows at once. Choosing a provider for the first time writes its default section ([MD-10](model.md#connecting-a-provider)). Before choosing a provider, Sushi asks the keychain again, so a key deleted elsewhere is noticed: the choice is not saved, and that provider's row says *No key for OpenAI is stored on this Mac any more. Connect OpenAI again to use it.*; the menu is built again when what is connected changed.
- **ST-22. Connecting and disconnecting.** A provider that is not connected shows what leaves the Mac and who pays, in the words of the connect screen ([MD-10](model.md#connecting-a-provider)): *Edits will go to OpenRouter: …*, and **Connect…**. A connected one says the same in the present tense, *Edits go to OpenRouter: …*; a connected one shows **Disconnect…**. Both run the native flows of [MD-13, MD-14 and MD-16](model.md#connecting-a-provider) as sheets of the window ([MD-17](model.md#connecting-a-provider)); the key is typed into a native field and never reaches the window's page ([MD-5](model.md#what-goes-out)). While a flow runs, its button reads *Connecting…* or *Disconnecting…* and is off; while a sign-in waits for the browser, **Cancel** next to it ends the wait and the row is as it was ([MD-14](model.md#connecting-a-provider)). The pane reads the files again when a flow ends.
- **ST-23. A provider's settings.** The details of a connected provider say *Key saved · checked when you run an edit*, then:
  - **Model ID**, free text, with a line on what edits use: *Edits use <model>.*, or *Not set in the file, so edits use <model>.*; **Use Sushi's default** removes `model` from the section, and when the section leaves options unset, a line says that it also brings back Sushi's defaults for them ([MD-10](model.md#connecting-a-provider)); **Browse models…** opens the provider's list of models in the browser;
  - under *Advanced*, the options the section may hold: *Reasoning effort* (OpenRouter, OpenAI), *Service tier* (OpenRouter), *Effort* (Claude), each offering the values of the schema (ST-31) and one more entry. When the file does not set the field, that entry is the current state, *Not set in the file · edits send high* or *Not set in the file · nothing is sent*; when it does, the entry removes the field, *Remove from the file — nothing is sent* or *Remove from the file — Sushi sends high*. When what the file sets differs from what an edit sends, the row says so (*Saved as high; edits send low.*, *Saved as high; this model's request does not send it.*).

  A first change for a provider whose section is missing writes its default section with that change, so the other options stay as they were in effect. A key of v0.2.1 in the section stays where it is and is never shown. Below, the details repeat what leaves the Mac and who pays, then **Disconnect…**.

### Actions

- **ST-24. The list.** The actions of `rules.json` in the order of the file, which is the order of the ⌘K list. **Add action**, **Duplicate**, **Move up** and **Move down** (also ⌥↑ and ⌥↓, and dragging) change the list. A deletion offers **Undo**, with no time limit; it writes back the action as the file last held it, even when its draft was not valid, and the draft stays a draft: it stays until the next change to the same list, and ⌘Z outside a text field undoes the latest deletion even after that. A deletion or a move of an action whose first save is still on its way is written after it. Every change writes the whole file (ST-12).
- **ST-25. An action.** The editor has *Name*; *Action type*, **Edit with the model** (`instruction`) or **Insert before the prompt** (`prefix`, [VH-12](version-history.md#what-changes-the-chain)); the instruction or the text to insert, multi-line, with every space and line break kept exactly as typed, and for inserted text a *Preview* of the result on a sample prompt; and *Phrases*, the aliases, where Return adds one. Switching the type keeps the other type's text until the change is saved. Under *File details* the *Action ID* is shown: it is made from the name when the action is created, made unique, and never changed by a rename, so the user never types an `id`.
- **ST-26. Checks.** An action is saved when it satisfies [LF-6](local-files.md#rulesjson--actions): a name, an instruction or a text to insert, no empty phrase. *Phrase used twice* flags an action whose phrase or name also finds another action, and the phrase says which one and what happens: dictated or pasted in ⌘K it runs the action that comes first in the list; typed, both are listed. The flag does not block the save, since the file allows it.

### Library

- **ST-27. The folder.** The pane shows the folder the Library reads, resolved as the panel's Library resolves it ([LF-11](local-files.md#library-prompts-and-templates)): its name and path, which wraps after a slash and not inside a name, how many prompts and templates it holds (a folder without `.templates` yet has 0 templates; when only `.templates` cannot be read, *N prompts · templates unavailable*), and where the choice comes from: *Default*, `library-path.txt` or `SUSHI_LIBRARY_DIR`. A folder that cannot be read shows *Unavailable: Sushi cannot read this folder.* When `library-path.txt` is invalid or unreadable, the pane shows the path the file says, no counts and *Not available until library-path.txt is fixed.*, and its banner says *The Library cannot open until the path is fixed.* (ST-13), with the panel's own message under **Error details**. **Show library in Finder** opens the folder when it can be read. **Choose folder…** opens the macOS folder picker as a sheet of the window; when the window is hidden before the picker shows, the choice counts as cancelled, and the picker never opens on its own; it selects another library, moves nothing, and writes the folder to `library-path.txt`, while a cancel writes nothing. The revision is checked after the picker closes; when the file changed meanwhile, the choice is not saved, and the conflict offers **Choose again…** (ST-11). **Use default folder** removes `library-path.txt`. With `SUSHI_LIBRARY_DIR` set, the pane says *Library folder set outside Settings*, that Sushi was started with it and must be restarted without it to choose a folder here, and its controls do not write.
- **ST-28. The dictionary.** *Dictionary* is a table of *Heard as* and *Written as* (`from` and `to`, [LF-9](local-files.md#dictionaryjson--dictation-terms)) with a filter, **Add term**, terms edited in place, and deletion with **Undo** as in ST-24, which writes back the term as the file last held it. A *Heard as* that another term already has, ignoring case and surrounding spaces, is refused at that field, and no other term is dropped to make the list fit. The pane says what the terms are for: *Look up these spellings in the Library (⌘L). Sushi does not replace text with them.*

### About

- **ST-29. The build.** The pane shows *Sushi <version>*, then **Copy build info**, which says *Copied* only once the copy went through, and buttons for the Documentation, the Release notes of this version and GitHub. **Build details** expands to the block of [BI-1](build-info.md#rules) and the short commit hash ([BI-4](build-info.md#rules)).
- **ST-30. Troubleshooting.** Each row has a heading and one control:
  - *Report a problem*: **Report a problem…** shows the panel at the first step of the report over the window ([RP-1](report.md#starting)). Leaving the report started here, with Esc or Cancel at any step or by copying it, hides the panel, so the window has the keyboard again ([PN-10](panel.md#hiding)).
  - *Log panel activity*: the switch over `diagnostics.json` ([LF-21](local-files.md#diagnosticsjson--recording-why-the-panel-hid)), and **Show log**. On writes `{"record": true}`, off writes `{"record": false}`, and the recording starts or stops at once. The switch shows what Sushi does now: the file's value, or, while the file is invalid or unreadable, the mode as it stays running, and it does not write until the file is fixed. While a problem report records, the switch gives way to *Recording for a problem report*, since the log is written either way. **Show log** shows the diagnostic log in Finder and is disabled until a log exists. A broken `diagnostics.json` affects only this row.
  - *Saved reports*: **Show in Finder** opens the folder of saved reports ([RP-8](report.md#the-report)), created when missing.
  - *Settings folder*: **Open settings folder** opens the settings folder ([LF-1](local-files.md#settings-folder)), created when missing.

### The schema

- **ST-31. Choices come from the validator.** The providers and the values a select offers (reasoning, tier, effort) are the validator's own lists, sent by Sushi to the window; the page holds no list of its own. A value outside them cannot be chosen, and one that reaches a save anyway is refused (ST-8).
- **ST-32. The schema and the app agree.** `make config-vet`, part of `make verify` and `make release-check`, checks that [`files.cue`](files.cue) and Sushi agree on the files:
  - it vets the shipped examples against their definitions;
  - a Rust test writes the window's choices and a corpus of files to `src-tauri/target/files-schema/`: files written by the window's save functions for `model.json`, `rules.json`, `dictionary.json` and `diagnostics.json`, every choice of every list included, `hotkey.json` as Sushi serializes it and as it may be written by hand, and files the validators refuse;
  - `.github/scripts/files-schema.mjs` compares the choices with the enums of `#Model` in `files.cue`, in order, and runs `cue vet` on every file: each accepted file must pass and each refused one must fail.

  Registering a key and putting the previous one back (ST-18) are not part of this check; the Rust tests of `hotkey.rs` and PR-13 cover them. Two checks remain Sushi's alone and are stated in `files.cue` and LF-18: whether the key of a shortcut is one Sushi knows, and that `library-path.txt` holds an absolute path. Modifier names are case-insensitive in both.

## Worked examples

**The window and the panel together (ST-2, ST-3, PN-9, PN-10).**

| From | What happens | Result |
| --- | --- | --- |
| The panel is shown | ⌘, or **Settings…** in the menu | The panel hides without giving the keyboard to the app underneath; the window takes it. |
| The window has the keyboard | The key that shows Sushi | The window stays open; the panel shows over it and takes the keyboard. |
| The panel is shown over the window | Esc, ⌘↵, or the key that shows Sushi | The panel hides; the window, or the sheet open on it, has the keyboard again. |
| The window has the keyboard | **Report a problem…** in About, then Esc, Cancel or Copy in the report | The panel shows the report over the window; leaving the report hides the panel, and the window has the keyboard again. |
| The panel is shown over the window | A click in the window | The panel hides; the window keeps the keyboard the click gave it. |
| The panel is shown | A click in another app | The panel hides; nothing is activated ([PN-5](panel.md#hiding)). |
| The window has the keyboard | ⌘W or the close button | The window hides; the panel does not show; the app the user came from is active again. |
| The window has the keyboard | **Choose folder…**, **Connect…**, **Disconnect…** | A sheet of the window opens; drafts stay. |

**Choosing a combination (ST-15 to ST-18).** In Keyboard, the user picks **Keyboard shortcut**; `hotkey.json` now holds `"capsLock": false` and ⌃⇧Space shows Sushi. They click **Change…** and press ⌥Space; while the keys are down nothing toggles the panel. On release, `hotkey.json` holds

```json
{
  "capsLock": false,
  "shortcut": "Option+Space"
}
```

⌥Space shows the panel, the status line says so, and **Show Sushi** in the menu carries ⌥Space as its shortcut. Had another app held ⌥Space, the file would be unchanged and the field would say *Sushi could not register ⌥Space: it was not saved. ⌃⇧Space still shows Sushi.*

**A backup combination (ST-15, ST-18).** With **Caps Lock** chosen and in effect, the user records ⌥Space as the backup. Sushi registers ⌥Space once, releases it, and writes `{"capsLock": true, "shortcut": "Option+Space"}`; Caps Lock still shows Sushi. Had another app held ⌥Space, nothing would be written: *Sushi could not register ⌥Space: it was not saved. Caps Lock still shows Sushi.*

**A hand edit under a draft (ST-10, ST-11).** The user types a new instruction for Shorten and leaves it empty for a moment, so it stays *Not saved*. Meanwhile they add an alias to Shorten in a text editor and save the file. Back in the window, the read finds the file changed under the draft. The pane says *Actions changed outside Settings.* and *Changed in the file: Shorten.*, and offers **Use the file's version** and **Replace with my version**; nothing is written until the user chooses.

**A broken file (ST-13).** `rules.json` has an entry with an empty name. The Actions pane says the actions could not be loaded, with `rules.json: entry 2 contains an empty field.` under **Error details**; the Keyboard, Model, Library and About panes work. **Restore default actions…**, once confirmed, keeps the broken file as `rules.invalid-20261124T101500Z.json` and puts back the six shipped actions; the panel's ⌘K lists them on its next show.

## Not supported or switched off

These are deliberate limits of v0.3.0, not defects. Changing any of them is a change of this specification.

- **The keys inside the panel** cannot be changed; Keyboard only lists them.
- **No search field** in the window, no themes, no setting for the size of the panel, and no opening at login.
- **Prompts and templates** are not edited in the window: they stay Markdown files in the library folder.
- **No list of models.** Model ID is free text; **Browse models…** opens the provider's own list. The local model is fixed ([LF-20](local-files.md#modeljson--the-model)).
- **No sync** of settings between Macs.
- **No live watching of the files.** A hand edit shows when the window gets focus or another of Sushi's writers changes a file (ST-5), not while the window keeps the focus.
- **An editor that saves at the same moment as the window can lose** (ST-10).
- **Drafts do not survive quitting Sushi** (ST-9).
- **The layout of a hand-written file is not kept** once the window writes it (ST-12).
- **A link or an unreadable file** is not written and not started over (ST-6, ST-14).
